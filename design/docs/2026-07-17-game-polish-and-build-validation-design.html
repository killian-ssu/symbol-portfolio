日期：2026-07-17 状态：待用户书面审阅

1. 背景与结论#

《远行商人》当前已经具备 40 件道具、10 张工具牌、5 个行动格、牌型、16 页关卡与特别状况等核心规则，纯规则测试能够覆盖全部道具、工具和特别状况。但玩家仍难以通过正常游玩判断：

  • 两件、三件和五件道具具体如何形成连锁；
  • 是否存在多个可行构筑方向，还是只有少数强势答案；
  • 某件道具是规则未生效，还是触发过程与文案没有表达清楚；
  • 爆分时应在哪个行动格、道具、分数区和过关节点得到反馈。

40 件不重复道具选择 5 件时有 658,008 种组合；因为向右紧邻传播依赖位置，考虑五个行动格顺序后有 78,960,960 种排列。再加入伙伴排列、工具牌、成长次数和特别状况，正常游玩不可能承担完整验证任务。

因此本轮采用“双线垂直切片”路线：先建立构筑验证能力，同时用一套代表性五道具连锁验证结算爽感。玩法、反馈和文案稳定后，再批量完成图标、弹窗、背景、胜负演出与声音。

2. 已确认范围#

2.1 本轮包含#

  1. 构筑实验室与自动批量模拟器。
  2. 40 件道具与 10 张工具牌的效果、文案、搭配和强度审计。
  3. 行动格、道具传播、分数区、目标达成与过关反馈。
  4. 四个地点的纯色动态背景和新地点场景包装。
  5. 道具/工具图标、奖励选择弹窗、详情弹窗、牌型和牌库界面。
  6. 单页完成、整局胜利与失败演出。
  7. 新音乐、音效分层与接入。

2.2 明确不包含#

  • 不增加货币、购买、出售、刷新商品或正式商店系统。
  • 不修改 eagle/wolf/turtle/bee/mouse、40 件道具和 10 张工具牌的稳定 ID。
  • 不恢复旧行动 ID、旧世界观或旧存档兼容层。
  • 不在 UI 中复制牌型、分数、目标合法性、触发顺序或奖励规则。
  • 不为局内工具目标选择增加新 Dialog 或全屏遮罩。
  • 不删除 build/、copyright/、tmp/ 或用户当前未提交的资源与 UI 修改。

用户口中的“商店”在本文中统一称为“奖励选择弹窗”，仍然执行当前的 2 件道具加 1 个工具组规则。

4. P0：当前基线收口#

4.1 高亮材质契约#

当前 CardTargetGlow.effect 定义完整的共享高亮参数，CardTargetGlow.mtl 只显式保存卡牌实例需要覆盖的颜色与速度，其余参数使用 Effect 默认值。现有静态测试要求 Material 重复保存全部参数，因而产生契约失败，但这不等于视觉效果失效。

收口策略：

  • 保留当前共享 Effect 和用户已经确认的手牌高亮视觉；
  • 卡牌、行动格和未来目标各自使用 Material 保存形状或颜色差异；
  • 测试改为验证共享 Effect 的完整控制项，并验证各 Material 只引用合法控制项；
  • 不为了通过测试回退用户当前视觉。

4.2 基线验收#

  • 纯规则测试继续保持全部通过；
  • UI 契约与当前可复用高亮结构一致；
  • 伙伴图标、伙伴卡背景、行动格背景与结算动画不回退；
  • Creator 继续打开唯一项目根目录，不创建 .worktrees/。

5. P1：构筑验证系统#

构筑验证系统由“可视化构筑实验室”和“无界面批量模拟器”组成。两者共享同一个场景数据协议，且只调用生产 Core，不复制玩法解释器。

5.1 统一场景数据#

BuildLabScenario 表达一次可重复的测试输入：

  • 固定随机种子；
  • 五个行动格的道具 ID 或空位；
  • 五个行动格的伙伴 ID；
  • 当前工具牌和本轮已使用工具；
  • 道具成长状态、伙伴累计成长和牌型永久加成；
  • 地点、页码、特别状况或无特别状况；
  • 需要运行的轮数与重复次数。

场景数据只描述输入，不包含“右侧意味着什么”“某道具如何算分”等玩法规则。所有效果继续由 JSON、V04GameSession 和 TriggerEngine 解释。

5.2 可视化构筑实验室#

实验室作为 assets/dev/ 下的开发专用入口，不进入正式游戏流程，也不改变 UIID.GameMain 的产品入口。

实验室必须提供：

  1. 为五个行动格选择、清空和交换任意道具。
  2. 指定五张伙伴牌及其排列。
  3. 指定工具牌、使用顺序和目标。
  4. 设置成长次数、地点和特别状况。
  5. 单步执行、完整播放、暂停、重播和重置。
  6. 显示行动格贡献、牌型倍率、最终分数、道具触发次数和伙伴再次行动次数。
  7. 按结算顺序显示事件轨迹：来源、目标、事件类型、批次数量和分数变化。
  8. 保存并载入具名预设；同一预设在相同种子下结果必须一致。

视觉播放应尽量复用正式 game_main 的 Board、HUD、浮字、道具锚点和结算播放器。实验室控制面板不得在正式发布构建中出现。

5.3 自动批量模拟器#

批量模拟器在无 Cocos 渲染环境下运行生产 Core，用于快速比较大量构筑。

首期扫描策略：

  • 完整枚举 1,560 个有序双道具布局；
  • 完整枚举 59,280 个有序三道具布局；
  • 对五道具布局按角色标签、位置和随机种子分层采样；
  • 使用一组固定伙伴排列、牌型、工具使用和成长档位作为标准场景；
  • 对高分异常组合追加不同伙伴排列、随机种子和特别状况复测。

输出指标：

  • 平均分、中位数、90/99 分位和最高分；
  • 各道具在高分样本中的出现率与位置分布；
  • 单件加入前后的边际增益；
  • 双道具、三道具协同倍率；
  • 触发次数、链深、启动成本和成长依赖；
  • 无效、弱协同、强协同与疑似失控组合；
  • 可复现的构筑预设和随机种子。

报告必须保留原始稳定 ID，并同时显示玩家名称，避免后续美术或文案改名导致结果无法追溯。

5.4 长链保护#

生产 Core 已支持压缩 SettlementBatch 和 ActionScoreBatch。实验室与模拟器不得逐个展开上亿次触发：

  • 统计使用批次总量和压缩序列；
  • 可视播放只展开前若干关键击，随后显示聚合次数与总贡献；
  • 报告标记使用批次结算、精度警告和异常高链；
  • 单次场景设置时间与事件上限，超限时返回明确诊断而非卡死。

6. P2：道具与工具审计#

6.1 单件审计卡#

每件道具和工具都记录：

  • 稳定 ID、玩家名称和当前短文案；
  • 触发时机；
  • 作用对象；
  • 原始行动、伙伴再次行动、道具再次触发之间的关系；
  • 跨轮成长与重置边界；
  • 最简单的正确使用示例；
  • 至少两个有意义搭配，或明确的独立用途；
  • 启动成本、稳定性、平均收益和爆发上限；
  • 当前问题与建议处理方式。

6.2 构筑方向#

首轮至少检查以下构筑族是否都能成立：

  1. 伙伴再次行动链。
  2. 道具再次触发链。
  3. 同伙伴相邻条件链。
  4. 不同伙伴相邻条件链。
  5. 工具牌驱动构筑。
  6. 成长累积构筑。
  7. 全局伙伴加成与牌型倍率构筑。

这些构筑族是分析标签，不是新增玩法规则。最终保留数量由模拟结果和实际体验决定。

6.3 文案合同#

玩家可见说明分成三层：

  • 卡面短句：只写核心效果，必须能在有限空间内读完；
  • 详情解释：补充触发时机、作用对象和成长边界；
  • 示例：用一个具体行动格排列说明结果。

如需增加详情或示例字段，应同步更新配置类型、严格校验器、DATA_SCHEMA.md 和测试。UI 不自行拼接规则含义。

6.4 首轮健康指标#

  • 每件道具有明确定位，不因无法触发或收益过低成为事实空白项；
  • 大多数道具至少有两个合理搭档，或有清晰的独立功能；
  • 至少五个构筑方向在标准场景下能形成可识别玩法；
  • 高分构筑需要布局、工具或成长成本，不由无条件单件道具垄断；
  • 高分样本中若单件道具出现率超过 40%，必须进行专项复测并解释原因；
  • 文案读者能够在结算前预测目标、方向和大致触发次数。

40% 是异常检查阈值，不是未经测试就执行的削弱规则。

7. P3：爆分反馈设计#

7.1 行动格与道具#

事件反馈
原始伙伴行动沿用格子压缩回弹，增加小型放射粒子与伙伴色闪光
道具触发道具锚点局部爆点、短闪和触发次数提示
右侧传播来源向右侧目标发送方向性光点或拖尾，目标产生抵达闪光
伙伴再次行动伙伴色环二次爆开，与原始行动使用不同节奏
道具再次触发道具外圈或贴纸式二次冲击，不与伙伴动画混淆
永久成长向上亮点、成长数字和短促强调音
超长批次关键击后转为聚合爆发、次数和总贡献，不逐击堆粒子

所有粒子锚点、颜色、速度、数量、曲线、尺寸和时长由 Prefab/Inspector 控制。运行时代码只根据 Core 事件选择并播放已绑定表现。

7.2 分数区与目标区#

  1. 每次有效伙伴贡献飞入分数区，分数按真实 ActionScoreBatch 累加。
  2. 牌型确定时，牌型与倍率区先锁定并强化，再开始逐格结算。
  3. 一轮总分完成时，分数区进行一次总冲击并把结果传向目标区。
  4. 达标时由目标区喷射金币、亮片或货品粒子；超额越高，表现等级越高。
  5. 粒子强度至少分为普通达标、明显超额、爆分三档，但达标判定与超额数值只来自 Core。

7.3 爽感验收#

  • 玩家能指出当前是哪个行动格和道具导致连锁扩大；
  • 原始行动、伙伴再次行动和道具再次触发可以仅凭表现区分；
  • 高链时不因重复动画拖慢到不可接受；
  • 最终分数与目标达成之间有清晰的能量传递和高潮；
  • 移动端不因局部与全屏粒子同时出现而产生明显掉帧。

8. P4：动态背景与地点场景#

新背景不继续以旧静态地图为主视觉，而采用纯色、低信息密度、持续运动的地点预设：

地点主色方向动态内容
雾叶林绿色、青灰雾带、叶片、柔和流动
回声湾蓝色、青色波纹、气泡、横向水流
风草坡金黄、橙色风线、草屑、斜向运动
晶砂谷紫红或晶蓝砂粒、晶体闪光、折射纹理

四套地点预设由 Prefab、Material 与 @property 保存。代码根据地点 ID 选择预设，不硬编码覆盖用户在 Inspector 中调整的颜色、速度或粒子参数。

当前旧场景名和旧地图资产只用于迁移定位，不继续作为玩家可见真相源。玩家界面统一使用雾叶林、回声湾、风草坡、晶砂谷和“特别状况”。

9. P5：图标与信息界面#

9.1 统一美术注册#

玩法 JSON 不写 SpriteFrame 路径。新增或整理统一的 Inspector 美术注册入口，以稳定 ID 映射道具与工具图标，并供以下界面共同读取：

  • 行动格道具；
  • 伙伴手牌中的工具牌；
  • 奖励选择弹窗；
  • 道具/工具详情弹窗；
  • 牌型与牌库界面。

不允许行动格有图、弹窗无图，或不同界面维护互相独立的 40 项映射。

9.2 界面完成条件#

  • 奖励选择弹窗继续显示 2 件道具和 1 个工具组，不出现价格或货币；
  • 详情弹窗显示图标、短句、解释与示例；
  • 牌型弹窗绑定 5 个启用牌型，显示当前预览牌型；
  • 牌库弹窗绑定 5 种伙伴与 10 张工具牌，显示实际持有数量；
  • 图标缺失时使用明确开发占位并输出诊断，正式验收时不得依赖同一张回退图覆盖多数道具。

10. P6：过关与胜负演出#

10.1 单页完成#

单页达标后先播放目标区喷射与短暂停顿，再打开奖励选择弹窗。该演出短于整局胜利，不遮盖上一轮连锁结果。

10.2 整局胜利#

  1. 最后一轮结算正常完成至目标达成。
  2. 局内表现层进入短暂局部慢放，保留背景与刚结束的行动画面。
  3. 画面压暗并短暂停留，音频降低。
  4. 亮色胜利遮罩展开，标题带预备、过冲和落定跳出。
  5. 后景与前景彩带按不同速度进入；现有礼花资产重新调整曲线、层次与密度。
  6. 按钮延迟出现，避免抢走标题和礼花开场。

慢放优先作用于结算与场景表现层，不修改会影响按钮、回调、关卡状态和 Dialog 生命周期的全局时间。

10.3 失败#

失败复用统一结果弹窗结构，但使用暗场、低密度尘粒、较慢标题和旅程摘要。失败不播放庆祝礼花和金币喷射。

11. P7：音乐与音效#

声音正式接入安排在主要动画时序稳定之后，避免反复重剪。资产与触发范围包括：

  • 主菜单主题；
  • 一条旅行主题的四地点变奏；
  • 普通结算、连续触发和高倍率三层结算声音；
  • 伙伴落位、道具触发、右向传播、成长、奖励出现；
  • 单页完成、整局胜利和失败短乐句；
  • 点击、关闭、刷新和非法操作。

程序侧负责播放分层、循环、淡入淡出、音乐压低和强度选择。最终音乐创作、授权与审美方向需要用户提供参考并审核。

12. 数据流与职责边界#

BuildLabScenario / 正式游戏输入
              ↓
        JSON + 生产 Core
              ↓
SettlementResult / SettlementBatch / ActionScoreBatch
        ↙                         ↘
批量模拟统计                 正式 UI / 可视实验室播放
  • Core/JSON：玩法、合法性、触发、分数、成长、奖励和随机结果。
  • 构筑实验室：选择输入、控制播放、展示 Core 输出。
  • 批量模拟器：生成场景、调用 Core、聚合结果。
  • 正式 UI：按批次播放，不重新计算。
  • Prefab/Inspector：布局、颜色、缩放、粒子、材质和动画参数。

13. 错误与诊断#

  • 未知稳定 ID：场景拒绝运行并显示精确字段路径。
  • 无效目标或工具步骤：使用 Core 的合法目标和禁用原因，不由实验室猜测。
  • 图标缺失：显示开发占位并列出缺失 ID。
  • 长链超限：保留总量、压缩批次与复现种子，停止逐击展开。
  • 同种子结果不同：视为确定性缺陷，必须在平衡比较前修复。
  • 配置、文档与代码冲突：以运行时 JSON/Core 为玩法真相源，以 v0.5 文档为玩家命名真相源，并先报告冲突。

14. 测试与验收#

14.1 自动测试#

  • BuildLabScenario 校验、序列化和固定种子复现；
  • 实验室与直接调用 Core 得到相同总分和批次；
  • 双道具与三道具枚举不产生未知 ID 或非法区域；
  • 长链保持批次压缩，不分配与触发次数等量的对象；
  • 报告统计的出现率、分位数、边际增益和协同倍率有固定样例；
  • 统一图标注册覆盖 40 件道具和 10 张工具；
  • 牌型、牌库、奖励、详情、过关和胜负弹窗保持 UI 契约。

14.2 手工验收#

  1. 在实验室中 1 分钟内搭出指定五道具组合并重复播放。
  2. 能从事件轨迹定位每一段右向传播和分数来源。
  3. 从模拟报告点选或复制异常组合后，可在实验室复现。
  4. 选择一套普通构筑、一套成长构筑和一套爆发构筑，三者反馈节奏可区分。
  5. 四地点背景的颜色与动态内容明显不同，但不干扰伙伴牌与分数阅读。
  6. 奖励、详情、牌型和牌库界面均显示正确图标与文案。
  7. 单页完成与整局胜利有不同强度；失败不会误用庆祝表现。
  8. 完成移动端性能、16 页流程和全部现有自动测试回归。

15. 协作与评审节奏#

每个阶段以一个可体验检查点结束：

  1. P1：用户用实验室试玩预设并确认是否足够快。
  2. P2：每批 8–10 件道具共同审阅文案与搭配，不一次堆完 40 件再返工。
  3. P3：只先完成一套代表性五道具连锁，确认信息量和爽感后铺开。
  4. P4/P5：背景、图标与弹窗先提供三个视觉方向，再选择一个正式制作。
  5. P6：分别审阅单页完成和整局胜利时间线。
  6. P7：以已锁定动画时序匹配音乐和音效。

首个实施计划只覆盖 P0 和 P1，不把后续所有美术与音频工作塞进同一次代码修改。
